# Ores & Drills

NeoForge-мод для Minecraft 1.21.1: многоуровневые буровые установки и настраиваемые крупные месторождения руд.

## Структура проекта

```text
src/
├── main/
│   ├── java/dev/
│   │   ├── OresAndDrillsMod.java  # точка входа и регистрация
│   │   ├── client/                   # клиентский рендер, экраны и создание мира
│   │   ├── command/                  # команды игрока
│   │   ├── compat/                   # необязательные интеграции (Jade)
│   │   ├── config/                   # конфигурация и пресеты мира
│   │   ├── drill/                    # реализации уровней буровых установок
│   │   ├── mixin/                    # минимальные Mixin-адаптеры Minecraft
│   │   ├── network/                  # payload'ы и регистрация сети
│   │   ├── registry/                 # все DeferredRegister-регистрации
│   │   └── world/                    # игровой домен: блоки, предметы, меню, мирогенерация
│   ├── resources/
│   │   ├── assets/ores_and_drills/ # клиентские ресурсы мода
│   │   ├── data/ores_and_drills/   # датапак-данные мода
│   │   ├── data/c/                   # common-теги
│   │   ├── data/minecraft/           # дополнения к vanilla-тегам
│   │   ├── ores_and_drills.mixins.json
│   │   └── pack.mcmeta
│   └── templates/META-INF/           # шаблон метаданных, обрабатываемый Gradle
└── test/java/                         # unit-тесты, повторяющие пакеты production-кода
```

`src/generated/resources` создаётся датагенератором и намеренно не хранится в Git. Папки `build`, `run`, `bin` и настройки IDE также являются локальными артефактами.

## Правила размещения нового кода

- Новый игровой контент размещайте в `world`: блоки — `world.block`, block entity — `world.block.entity`, предметы — `world.item`, меню — `world.inventory`.
- Код, относящийся только к конкретной буровой установке, держите рядом в `drill`; общую механику — в `world`.
- Не регистрируйте объекты внутри игровых классов: добавляйте их в подходящий класс `registry/`.
- Клиентский код не должен попадать в common-пакеты; для него используйте `client/`.
- JSON-модели, blockstate, языки и текстуры относятся к `assets/<mod_id>/`; рецепты, loot tables, теги и biome modifiers — к `data/<namespace>/`.
- На каждую изолированную математическую или конфигурационную часть добавляйте тест в зеркальный пакет `src/test/java`.

## Поиск месторождений

Операторская команда имеет одну форму:

```text
/locate oredeposit <ore> <tiny|small|medium|large>
```

`<ore>` проверяется и дополняется по актуальному серверному тегу `#c:ores`. Все физические блоки
месторождения заменяют только `#c:stones`. Поиск идёт по независимой сетке выбранного размера в
горизонтальном радиусе 20 000 блоков и не загружает удалённые чанки.

`tiny` и `small` сначала ищут реальную горизонтальную стену пещеры и строят связную форму от её
поверхности внутрь `#c:stones`. Если подходящей стены нет или из неё нельзя построить корректную форму,
тот же seed-кандидат использует обычную подземную линзу; отмена происходит только тогда, когда нет и
подходящей породы. Для ещё не сгенерированных чанков команда проверяет гарантированный подземный fallback
по базовой породе, не загружая удалённые чанки; реальная стеновая форма после генерации заменяет прогноз
подтверждённой записью. Параметр common-конфига `ore_deposits.strict_wall_deposit_locate=true` оставляет
только фактически созданные записи из `ConfirmedDepositIndex`.

Основные части реализации находятся в `dev.world.level.levelgen`:

- `DepositLayouts`, `TierDepositResolver` и четыре resolver задают независимые сетки и seed-пространства;
- `CaveWallDetector`, `CaveWallAnchor` и `WallDepositGeometry` отвечают за стену, глубину и связную форму;
- `OreDepositFeature` приоритетно размещает стеновые формы и использует подземный fallback;
- `DepositLocator` разделяет подтверждённые и seed-предсказанные результаты;
- `ConfirmedDepositIndex` хранит подтверждения через `SavedData`, а `DepositValidationCache` кеширует проверки;
- `OreDepositLocateCommand` регистрирует Brigadier-команду, автодополнение и кликабельные координаты.
